什么是 screen？两个死比喻彻底讲透

如果把开发者写代码比作去高铁站坐车，AI 审查其实分成了两种完全不同的角色：

传统 AI 审查 · 深度会诊
👨‍⚕️ 🩺 📜
3 位老中医坐诊，手写 800 字调理报告
场景：你只想刷卡进站，门口却强制安排了 3 位资深老中医给你把脉。
  • • 每个人要闭目思考 40 秒，仔细看你的面相和舌苔；
  • • 每个人拿毛笔工整写出 800 字的就医、起居与饮食建议；
  • • 结果：诊断极深极准，但排队排了 2 小时，车早开走了（Git Push 超时卡死）。
适合：重大疑难杂症（核心架构 PR 深度会诊）
pi-review screen · 秒级安检
🚇 🎒 🚨
进站口的行李 X 光安检机
场景：行李（代码）滑过履带，传感器 1.0 秒钟扫一下透视图。
  • • 它不给你写养生建议，它只看有没有带管制刀具（SQL 注入、数组越界）；
  • • 扫到危险品瞬间 「嘀嘀嘀」 报警把你拦下，红灯标出第几行；
  • • 没带危险品 「滴」 一声 1.0 秒直接放行（零等待丝滑进站）。
适合：日常刷卡进站（Git Hook / CI 极速门禁）
⚡️
为什么 screen 能从 80 秒压缩到 1.0 秒？
秘密在于「不写大作文，改刷机读卡」：
传统审查最慢的是大模型现场逐字生成 1000 字长篇散文；
screen 是把代码切成小块，在 1 秒内用光学机读卡连刷 108 道判断题（有没有越界？有没有漏 await？）。只拿概率评分，在本地直接查表贴标签，把耗时最长的大模型写作文环节彻底砍掉了。

pi-review screen
1.0 秒瞬间拦截
专门定位为「极速安检门」。跳过大模型散文生成，采用声明切片与单次 Jev 概率决策，在 1 秒内给出精准的二值拦截信号。
  • ✓ 零感知推入 Git Hook：1.0 秒执行完毕，完美契合 pre-commit / pre-push 的交互要求。
  • ✓ 零消耗评委 Token 额度：走专属 System One 通道，不占用主评委上下文窗口与并发配额。
  • ✓ 精准标准化组装：行号来自切片器，修复指南来自专家模板，直奔主题、即刻修改。
📐 三步零生成架构：从代码到门禁
关键路径上没有任何 LLM 散文生成，全流程在本地计算与单次轻量 HTTP 决策之间穿透：
STAGE 01 · 本地毫秒级
确定性语法切片
本地切片器按 class / method / interface 边界切分出独立 Hunk，锁定物理行号。
➔
STAGE 02 · 1.0 秒决策
单次 Jev 并行微决策
单次调用向 TypeSafe Jev 发送 108 道判定题（兜底通用题 + 8 大模式题），瞬时返回概率向量 P。
➔
STAGE 03 · 本地毫秒级
模板装配与门禁判定
P ≥ 0.6 触发模式模板组装 Finding，存在高危缺陷立即 exit 1 阻断，干净则 exit 0。
ReviewFinding 各字段产生机制清单：
Finding 字段 产出源 机制说明 耗时贡献
id, path, location 本地语法切片器 确定性解析函数/类起始与结束行号 < 1 ms
actionable Jev 概率阈值 Jev 返回缺陷概率 $p \ge 0.6$ 自动标记为 true 0 ms

🎯 内置 8 大高危代码缺陷探测雷达
off_by_one_loop Critical
循环下标越界读取
循环条件使用 i <= length 导致末次访问 undefined 触发运行时崩溃。
for (let i = 0; i <= items.length; i++)
unawaited_async Critical
异步调用丢失 await
数据库写入未挂起等待，导致未捕获拒绝以及邮件在落库前提前发出的时序错乱。
this.db.query("INSERT INTO ...") // no await
sql_injection Critical
字符串拼接 SQL 注入
在查询中直接使用模板字符串插值拼接未经清洗的参数，造成注入漏洞。
`SELECT * WHERE id = '${customerId}'`
slice_off_by_one Major
切片越界截断丢数据
slice(start, end - 1) 对本身非包含的 end 多减了 1，导致分页末位元素永久丢失。
return items.slice(start, end - 1);
float_equality Major
浮点精确判等异常
在循环分支中对累计金额做 === 100.0 判等，受精度影响导致提早异常中断。
if (total === 100.0) return total;
float_money Major
浮点数直接累加货币
直接使用浮点数做交易金额累加，随着流水规模增长产生分厘账目对账故障。
total += order.total; // float
cache_aliasing Minor
缓存共享可变引用
从内存 Map 取出的对象未做深浅拷贝直接修改，导致调用方脏写与状态分裂。
order.status = "shipped"; cache.set(id, order);
missing_validation Minor
边界缺乏防御性校验
信任边界对空数组、负数、未定义入参不做前置防御，异常穿透至深层引发 Crash。
placeOrder(id, items) // no validation

🚀 四大工程落地场景
SCENARIO 01
Git 本地零感知推送拦截
在开发者执行 git push 时，以 1 秒内的心流体验秒级拦截越界、注入等低级错误，脏代码绝不出本地机器。
# .husky/pre-push STAGED=$(git diff --name-only origin/main...HEAD) pi-review screen $STAGED || exit 1
SCENARIO 02
CI/CD 差异化两段式门禁
在 GitHub Actions 中作为 Stage 1 运行。1 秒内快速打回有问题的 PR，完全不用等待后面数分钟的构建镜像与全量单测。
# .github/workflows/ci.yml - name: Fast Gate Screen run: pi-review screen ${{ steps.files.outputs.all }}
SCENARIO 03
Monorepo 变更大仓前置分诊
面对同时改动几十个模块的巨大提交，先用 screen 进行极速扫描，仅将亮红灯的核心模块交由大模型会诊，节省 90% 审查开销。
pi-review screen @packages/* # 仅对标红的 package 拉起 --reviewers 3
SCENARIO 04
Agent 闭环修复的冒烟初筛
在 Agent 运行 loop --until clean 循环修复代码时，每一轮先用 screen 冒烟，最基本的编译与语法问题未修好前直接打回重修。
# Agent 内部守卫逻辑 if screen(patch) == 0: run_full_panel_loop()
🌲 代码审查模式选型决策树
根据审查所处的生命周期与容忍耗时，选择最贴合工程实际的运行策略：
代码变更准备进入审查流程 │ ├─► 是 Pre-commit / Pre-push 钩子或 CI 快速阻断？ │ └─► pi-review screen（1.0 秒瞬间拦截，0 等待心流） │ ├─► 需要多模型独立背书、消除主观臆断？ │ └─► pi-review --reviewers 3（多数票 Quorum，过滤孤证误报） │ ├─► 是 Agent 自动化修复、需要多轮验证收敛？ │ └─► pi-review loop --until clean（*必须开启 Jev 保持跨轮状态记忆*） │ └─► 只是本地日常功能自查？ └─► pi-review review（单模型深度细审，获取修复建议）
