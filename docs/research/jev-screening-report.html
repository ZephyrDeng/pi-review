🧠 工程隐喻：如何向技术团队解释 screen 的定位？
Engineering Mental Model · to-humans
L4 网络快速包过滤 vs L7 深度报文应用审计
在工业级高并发网关中，没有任何系统会对全量流量直接拉起深度 L7 报文重组与语义审计。工程系统的标准解法永远是分层漏斗（Layered Funnel）：
传统 LLM 审查 (review / panel) L7 深度语义审计
类比：对每一个入站 TCP 请求做全量上下文追踪、AST 跨文件还原、调用链推导，并生成 1000 字的架构诊断日志。
  • • 耗时下限：受大模型逐字吐 Token 物理限制，耗时锁定在 30s ~ 80s+；
  • • 配额开销：消耗昂贵的主模型 Token 上下文与 API 并发额度；
  • • 工程结果：诊断极深，但挂在 Git Hook 里会导致开发者频繁使用 --no-verify 绕过。
定位：疑难杂症攻坚、PR 合并最终专家会诊
pi-review screen L4 极速特征旁路过滤
类比：在网卡驱动层部署高性能 Syn-cookie 与硬件 ACL 规则，1.0 秒扫描数据包特征，发现异常立即 RST 阻断。
  • • 零散文生成：不写解释性作文，只做 p > 0.6 的二值概率判断；
  • • 零评委负担：走独立的 System One 极速旁路，0 消耗主模型 Token；
  • • 工程结果：耗时 1.0 秒，开发者毫无卡顿感知，脏代码根本出不了本地机器。
定位：Git Pre-push 钩子、CI/CD 极速 Fail-Fast 哨卡
⚠️ 隐喻的边界（Where the metaphor breaks down）：
screen 并不是简单的正则匹配或传统 AST Linter。静态规则很难捕获像 float_equality（复杂的浮点判等上下文）或 cache_aliasing（隐式指针可变共享）这种带有语义倾向的深层缺陷。screen 背后是具备代码理解能力的 TypeSafe System One 模型，它拥有 LLM 级的语义穿透力，但通过限制输出格式规避了文本生成的延迟惩罚。
📐 三步零生成架构：从源文件到 Exit Code
去除大模型逐字输出的瓶颈，全流程在本地内存计算与单次 HTTP 概率探测之间流水线流转：
STAGE 01 · 本地毫秒级
声明式语法切片
本地切片器按 class / method / interface 边界将源码切分成独立的逻辑代码块 (Hunk)，锁定物理起始行号。
➔
STAGE 02 · 1.0 秒网关
单次 Jev 并行微决策
单次 HTTP 请求向 TypeSafe Jev 发送 108 道判定题（兜底通用题 + 8 大模式题），并行返回各模式置信概率向量 P。
➔
STAGE 03 · 本地毫秒级
查表装配与门禁阻断
概率 p ≥ 0.6 触发对应缺陷模式的标准修复模板，组装 Finding。发现高危缺陷立即以 exit 1 阻断。
ReviewFinding 各字段解构清单：
字段 产出源 工程机制 延迟贡献
id, path, location 本地语法切片器 确定性解析类/函数起始与结束行号 < 1 ms

🎯 内置 8 大高频代码缺陷探测雷达
off_by_one_loop Critical
循环越界访问
循环条件使用 i <= length 导致末次访问 undefined 触发运行时 Crash。
for (let i = 0; i <= items.length; i++)
unawaited_async Critical
异步落库漏 await
数据库插入未等待 Promise，导致未捕获拒绝以及对外通知在落库前提前触发。
this.db.query("INSERT INTO ...") // 悬空
sql_injection Critical
模板字符串拼接 SQL
在查询语句中直接使用字符串插值拼接未经清洗的参数，造成高危 SQL 注入。
`SELECT * WHERE id = '${customerId}'`
slice_off_by_one Major
分页切片边界偏移
slice(start, end - 1) 对本身非包含的 end 多减 1，导致分页末位元素永久丢失。
return items.slice(start, end - 1);
float_equality Major
浮点数直接严格判等
在循环中对累加浮点数使用 === 100.0，受 IEEE 754 精度影响导致提前异常中断。
if (total === 100.0) return total;
float_money Major
浮点数直接累加货币
直接使用浮点数做交易金额累加，随着订单量增长产生对账分厘误差。
total += order.total; // 浮点累加
cache_aliasing Minor
缓存共享可变引用
从内存 Map 取出的对象未做深浅拷贝直接修改，导致调用方脏写与状态分裂。
order.status = "shipped"; cache.set(id, order);
missing_validation Minor
边界缺乏入参防御
公共接口对空数组、负数、未定义入参不做前置防御校验，异常穿透至深层。
placeOrder(id, items) // 无入参守卫

🚀 四大工程落地场景
SCENARIO 01
Git 本地零感知推送拦截
在开发者执行 git push 时，以 1 秒内的极速体验秒级拦截越界、注入等低级错误，脏代码绝不出本地机器。
# .husky/pre-push STAGED=$(git diff --name-only origin/main...HEAD) pi-review screen $STAGED || exit 1
SCENARIO 02
CI/CD 差异化两段式门禁
在 GitHub Actions 中作为 Stage 1 运行。1 秒内快速打回有问题的 PR，完全不用等待后面数分钟的构建镜像与全量单测。
# .github/workflows/ci.yml - name: Fast Gate Screen run: pi-review screen ${{ steps.files.outputs.all }}
SCENARIO 03
Monorepo 变更大仓前置分诊
面对同时改动几十个模块的巨大提交，先用 screen 进行极速扫描，仅将亮红灯的核心模块交由大模型会诊，节省 90% 审查开销。
pi-review screen @packages/* # 仅对标红的 package 拉起 --reviewers 3
SCENARIO 04
Agent 闭环修复的冒烟初筛
在 Agent 运行 loop --until clean 循环修复代码时，每一轮先用 screen 冒烟，最基本的编译与语法问题未修好前直接打回重修。
# Agent 内部守卫逻辑 if screen(patch) == 0: run_full_panel_loop()
🌲 代码审查模式选型决策树
根据代码所处的生命周期、上下文依赖程度与工程容忍耗时，选择匹配的审查策略：
代码变更准备进入审查流程 │ ├─► 是 Pre-commit / Pre-push 钩子或 CI 快速阻断？ │ └─► pi-review screen（1.0 秒瞬间拦截，0 等待心流） │ ├─► 需要多模型独立背书、消除主观臆断？ │ └─► pi-review --reviewers 3（多数票 Quorum，过滤孤证误报） │ ├─► 是 Agent 自动化修复、需要多轮验证收敛？ │ └─► pi-review loop --until clean（*依靠 Jev 保持跨轮状态记忆*） │ └─► 只是本地日常功能自查？ └─► pi-review review（单模型深度细审，获取修复建议）
