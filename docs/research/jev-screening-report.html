pi-review screen
1 秒跑完的代码检查

提交代码前跑一次，1 秒内扫出 8 类最常出事的缺陷（数组越界、漏写 await、SQL 注入、浮点误差……），直接告诉你在哪一行、什么问题、怎么改。同一份代码，传统大模型审查要跑 78 秒。

一句话说明 (TL;DR)
从 80 秒 → 1 秒：不打断开发心流
对于 i <= length 数组越界这种低级错误，你不需要大模型现场写一篇 800 字的分析报告。你只需要在 1 秒内被告知「第 43 行越界了，回去改 < 符号」，screen 只干这件最实用的事。
耗时对比实测（同一份 106 行服务） 0s → 80s
传统大模型审查 78.1 秒
pi-review screen 1.0 秒
📐 它是怎么跑得这么快的？三步走架构
第 1 步 · 本地计算
本地声明切片
把你的源码按 class / method / interface 边界切成一个个小块（类似 IDE 的折叠页签），纯本地计算，耗时忽略不计。
➔
第 2 步 · 单次请求
单次 Jev 概率打分
对每个小块连发 9 道精准判断题（有没有越界？有没有 SQL 注入？），在单次 HTTP 请求中瞬间打完 108 道题并返回概率。
➔
第 3 步 · 本地查表
查表组装与门禁
只要有缺陷概率 > 0.6 就查出对应的标准修复模板，弹出红牌 exit 1 拦截，完全干净则 exit 0 放行。
关键点：它砍掉的是传统大模型「逐字写报告」的生成环节。逐字吐 Token 是物理层面的耗时大头，而 screen 只让 Jev 做选择题和打分题（单次轻量 API 调用），所以快得高谱。
🎯 内置 8 类高频缺陷模式
循环越界 Critical
数组越界访问
循环条件多走一步，最后一个下标访问到 undefined，运行时直接抛错。
for (let i = 0; i <= items.length; i++)
异步悬空 Critical
未等待的异步写入
数据库写入未 await，函数提前返回；写失败只产生未捕获的 Promise 拒绝，内存与数据库状态不一致。
this.db.query("INSERT INTO ...") // 没有 await
SQL 注入 Critical
字符串冒接 SQL 参数
参数以模板字符串直接拼进 SQL，输入 ' OR '1'='1 即可读取全表。
`SELECT * WHERE id = '${customerId}'`
切片偏小 Major
slice end 多减 1
slice 的 end 本身不包含，再减 1 后每页固定少返回最后一条数据。
return items.slice(start, end - 1);
浮点相等 Major
浮点数直接判等
浮点累加后直接判等，0.1 + 0.2 !== 0.3，分支判断与循环终止条件不可靠。
if (total === 100.0) return total;
浮点算钱 Major
用浮点数累加金额
float 累加误差随订单量累积，最终对账出现分位偏差。
total += order.total; // 用 float 算钱
内存脏写 Minor
缓存对象共享引用
缓存直接返回对象引用，外部修改会写回缓存，DB 回滚时内存与持久层状态分裂。
order.status = "shipped"; cache.set(id, order);
缺少校验 Minor
公共入口缺少入参校验
对空数组、负数、undefined 不做校验，异常穿透到深层调用栈。
placeOrder(id, items) // 无入参守卫
🚀 前端实战：三个落地场景
SCENARIO 01
Git 推送 1 秒飞速拦截
在 git push 时以闪电速度阻断越界、注入等低级拼写与逻辑错误，绝不拖延开发者心流。
# .husky/pre-push PATCH=$(git diff origin/main...HEAD) pi-review screen $PATCH || exit 1
SCENARIO 02
CI 流水线前置杀手
作为 GitHub Actions 的第一步运行。1 秒内把有问题的 PR 打回，完全不用等待后面几分钟的镜像构建和单测。
# .github/workflows/ci.yml - run: pi-review screen ${{ steps.files.outputs.all }}
SCENARIO 03
Monorepo 大仓前置分诊
面对同时改动二三十个模块的大版本提交，先用 screen 极速过筛，仅把亮红灯的模块留给大模型面板。
pi-review screen @packages/* # 仅对标红的 package 启动 panel
🧭 调用建议图：什么场景用哪个命令
先判断「你的审查处在哪个环节」，再选命令
四个分支对应四种命令，各自标出关键参数、实测耗时与退出码语义。
命令 什么时候用 不要用在这里 关键参数
screen Pre-commit / Pre-push 钩子，CI 的第一道快速打回，几十个变更文件的分钟级分诊 需要跨文件推导、架构级建议、完整证据链的场合 无需额外参数；需要 TYPESAFE_API_KEY
--reviewers N PR 合并前，安全 / 支付 / 权限等敏感模块，需要独立发现做交叉验证 本地单人迭代阶段（成本与耗时都不划算） --consensus quorum --min-agree 2
loop Agent 自动修复后的回归验证；需要「改一轮、审一轮」直到收敛 代码在两轮之间不会变动的场景（会得到 non_converging） --until clean --max-rounds 10
review 本地开发自查：一个模型读完代码，给出带证据与修改建议的完整报告 需要秒级返回的 Git Hook（改用 screen） --model <provider/model[:thinking]>
两段式组合最常用：screen（~1 秒）先把低级缺陷挡在门外，loop --until clean（每轮 20 秒起）在流水线里做多轮收敛。两者共用同一套退出码语义：0 干净 · 1 有 findings · 2 参数错误 · 3 需人工 · 4 运行失败。
