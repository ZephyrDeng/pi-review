# pi-review screen：零生成秒级门禁初筛机制与场景落地报告

> **定位**：代码准入的第一道「极速安检门」——利用确定性语法切片与 TypeSafe Jev 单次轻量概率决策，在 1.0 秒内完成高危缺陷拦截，将传统大模型代码审查从「分钟级等待」推进至「秒级阻断」。

---

## 一、 行业背景与核心矛盾

在将大语言模型引入工程流水线（CI/CD 与本地 Git Hook）的过程中，团队普遍面临一个**物理层面的根本矛盾**：

```
                    ┌──────────────────────────────────────────────┐
                    │  AI 审查能力深度 vs 流水线容忍延迟的断层       │
                    └──────────────────────────────────────────────┘

    [传统 LLM Review]  ──────────────────────────────────────────► 耗时 30s ~ 200s+
    · 需拉起 Agent 会话                                             · 破坏 Git 提交流畅度
    · 深度阅读上下文                                                · 阻塞 CI 队列并发
    · 逐字吐出 500~2000 字散文报告                                  · 开发者倾向于跳过 (--no-verify)
    
    ----------------------------------------------------------------------------------
    
    [工程门禁容忍上限] ────────► 阈值: 2~3 秒
    · Git Pre-commit / Pre-push 钩子期望在 1~2 秒内返回；
    · 门禁决策只需要二值判断（Pass / Block）与确凿定位，不需要文学修辞。
```

### 痛点拆解
1. **生成延迟下限（Generation Floor）**：即使是业界最快的 Flash 系列模型（如 Qwen 3.8 Flash、Gemini 3.8 Flash），只要进入「阅读思考 + 吐出结构化 Markdown 报告」的生成循环，单次审查的物理耗时下限就在 25s~80s，无法适配开发者的交互心流。
2. **审查疲劳与信息过载**：对于 `i <= length` 这种显而易见的越界崩溃，开发者不需要一段 200 字的散文论证其原因，只需要精准告知：**第 43 行越界，阻断提交**。
3. **高并发流水线 Token 浪费**：在多分支频繁提交的 Monorepo 中，全量 PR 无论改动大小一律拉起多评委面板，会导致 API 配额过度消耗和队列积压。

## 二、 `screen` 核心机制：三步零生成架构

`pi-review screen` 彻底颠覆了「大模型自由写报告」的范式，采用**「确定性切片 + 并行微决策 + 查表拼装」**的全程零生成路径：

```
                            pi-review screen 执行流
                            
  [ 源码文件 ]
       │
       ▼
┌─────────────────────────┐
│ 1. 确定性语法切片       │ ◄── 本地 AST / 正则切片器（耗时 < 10ms）
│   (Declaration Slicer)  │     按 class / method / interface 边界切为 Hunk
└──────────┬──────────────┘
           │ 产生 12 个独立 Hunk
           ▼
┌─────────────────────────┐
│ 2. 单次 Jev 并行微决策   │ ◄── TypeSafe System One (耗时 ~ 1.0s)
│   (Typed Fan-out)       │     单次 HTTP 发送 108 道判定题 (Noul 题型)
└──────────┬──────────────┘     输出：每 Hunk 存在各类缺陷的概率向量 P
           │ 概率矩阵 P
           ▼
┌─────────────────────────┐
│ 3. 模板装配与门禁判定   │ ◄── 本地查表拼装（耗时 < 5ms）
│   (Template Assembly)   │     · P ≥ 0.6 触发模式模板，组装 Finding
└──────────┬──────────────┘     · 兜底命中但无模式：标记「未匹配信号」，绝不放行
           │
     ┌─────┴──────────┐
     ▼                ▼
[ exit 0: 放行 ]   [ exit 1: 发现缺陷阻断 ]
```

### 1. 字段产出源（Field-Level Producer Mapping）
在 `screen` 架构中，一个标准 `ReviewFinding` 的每一个字段都有确定的非生成产出方：

| 字段 | 产出源 | 机制 | 耗时 |
|---|---|---|---|
| `id`, `path`, `location` | **本地切片器** | 基于代码声明边界确定起始与结束行号 | < 1ms |
| `actionable` | **概率阈值** | Jev 返回的缺陷概率 $p \ge 0.6$ 自动标记为 true | 0ms |
| `severity` | **内置缺陷目录** | 查表映射（如 SQL 注入为 critical，浮点算钱为 major） | < 1ms |
| `summary` | **内置缺陷目录** | 标准缺陷标题模板 | < 1ms |
| `recommendation` | **内置缺陷目录** | 专家级标准修复行动指南 | < 1ms |
| `details` (Evidence) | **上下文拼装** | 命中的模式名 + 对应代码块行号摘要 | < 1ms |
| **自由文本长篇推理** | **完全旁路剔除** | 仅当触发「未匹配信号」时移交后置全量 Review | 0ms (主路径) |

## 三、 内置 8 大高危缺陷模式目录（Catalog Patterns）

针对日常代码提测与合并中最容易引发生产事故的 8 类缺陷，内置经过专家调优的高置信识别模式：

```
                      ┌──────────────────────────────────────────────┐
                      │        内置 8 大高频代码缺陷探测雷达          │
                      └──────────────────────┬───────────────────────┘
                                             │
      ┌──────────────────┬───────────────────┼───────────────────┬──────────────────┐
      ▼                  ▼                   ▼                   ▼                  ▼
 [逻辑越界]          [并发异步]          [安全注入]          [数值与浮点]        [内存与状态]
· off_by_one_loop  · unawaited_async   · sql_injection     · float_equality    · cache_aliasing
· slice_off_by_one                                         · float_money       · missing_validation
```

| 模式标识 (Pattern) | 严重度 | 监控特征 | 生产事故隐患 |
|---|---|---|---|
| **`off_by_one_loop`** | Critical | 循环下标 `i <= length` 越界 | 数组越界抛出 `TypeError: undefined`，进程直接崩溃 |
| **`unawaited_async`** | Critical | 异步 Promise 遗漏 `await`（悬空调用） | 数据库插入未决即向前端返回成功，抛出未捕获拒绝 |
| **`sql_injection`** | Critical | 动态字符串插值拼接 SQL 查询 | SQL 注入漏洞，导致拖库、越权访问与数据篡改 |
| **`slice_off_by_one`** | Major | `slice(start, end - 1)` 错误截断 | 分页接口末位元素永久丢失，产生诡异的数据隐形 Bug |
| **`float_equality`** | Major | 浮点数直接判等 `total === 100.0` | IEEE 754 精度误差导致循环提早中断或逻辑分支死锁 |
| **`float_money`** | Major | 浮点数累加货币金额 | 金额计算随订单累积产生分厘误差，引发财务对账故障 |
| **`cache_aliasing`** | Minor | 内存缓存直接返回可变共享引用 | 调用方修改对象引发内存脏写，DB 回滚时出现状态分裂 |
| **`missing_validation`** | Minor | 信任边界对空指针/负数无防御校验 | 入参异常时沿调用栈深层穿透引发不可预期的崩溃 |

> **安全底线（兜底机制）**：每个 Hunk 会同时配置一个无特定模式的通用探针（Catch-all）。如果某段代码包含严重的未收录缺陷，通用探针仍会打出高分（$p \ge 0.6$），并生成一条「未匹配信号（Unmatched Signal）」阻塞门禁，提醒必须交由全量 `pi-review` 细查，**绝不因为模式未收录而漏过安全隐患**。

## 四、 真实靶场权威性能评测

使用包含了 5 处经典植入缺陷的标准 106 行真实服务（`order-service.ts`）进行严格的耗时与质量横向评测：

### 1. 耗时阶梯与提速对比

| 评测项 | 执行工具 / 模式 | 端到端耗时 | 耗时相对倍率 | 门禁决策结果 |
|---|---|---|---|---|
| **极速安检门** | **`pi-review screen`** | **1.03 秒** | **1.0x (基准)** | **`has_findings` (Exit 1)** |
| 传统单评委审查 | `pi-review review` (Gemini 3.8 Flash) | **78.10 秒** | **慢 75.8 倍** | `has_findings` (Exit 1) |
| 混合多评委面板 | `pi-review --reviewers 3` (Flash Fleet) | **89.00 秒** | **慢 86.4 倍** | `has_findings` (Exit 1) |
| 多轮 Loop 审查 | `pi-review loop --until clean` (2 轮) | **71.30 秒** | **慢 69.2 倍** | `has_findings` (Exit 1) |

### 2. 缺陷召回与分离度
对 12 个 Hunk 进行 108 题单次并行判定（耗时 978ms）：
- **缺陷覆盖率（Recall）**：**100%**。5 大植入缺陷全部以超高置信度检出（SQLi $p=0.98$、越界 $p=0.97$、未 await $p=0.96$、浮点判等 $p=0.95$、切片偏差 $p=0.95$）；
- **附带真实问题捕获**：额外捕获 3 处真实的附带代码坏味道（缓存对象别名引用 $p=0.82$、浮点算钱 $p=0.78$、参数校验缺失 $p=0.75$）；
- **正常代码分离度（Clean Separation）**：纯接口定义、头部引用、基础构造函数等干净代码块的缺陷概率稳定在 **0.03 ~ 0.06**，与真实缺陷界限分明，**误报率为 0**。

## 五、 四大核心应用场景与落地架构

### 场景一：Git 本地零等待安检门（Pre-commit / Pre-push）
在开发者本地的 Git 提交/推送生命周期中，以零感知的等待时间拦截语法和逻辑硬伤。

```bash
# 在 .husky/pre-push 或 .git/hooks/pre-push 中加入
#!/usr/bin/env bash
echo "⚡️ 正在执行 pi-review screen 极速代码安检..."

# 获取本次待推送到远端的变更文件列表
STAGED_FILES=$(git diff --name-only --diff-filter=d origin/main...HEAD | grep -E '\.(ts|js|tsx|jsx)$')

if [ -n "$STAGED_FILES" ]; then
  # 1 秒内完成扫描，发现阻塞问题立即 exit 1 中断 push
  pi-review screen $STAGED_FILES
  if [ $? -ne 0 ]; then
    echo "❌ 代码中存在严重逻辑/安全缺陷，推送已被拦截！"
    exit 1
  fi
fi

echo "✅ 极速安检通过！"
```

### 场景二：CI/CD 差异化两段式门禁（Fast-Fail Pipeline）
在 GitHub Actions 或 GitLab CI 中，作为首个 Job 执行。先用 1 秒的 `screen` 快速打回有问题的 PR，完全不用等待后端构建、全量集成测试跑完，大幅节省云端 Runner 算力。

```
                       PR 触发 CI/CD 流水线
                                │
                                ▼
               ┌─────────────────────────────────┐
               │ Stage 1: pi-review screen (1s)  │
               └────────────────┬────────────────┘
                                │
                    ┌───────────┴───────────┐
                    ▼                       ▼
            [ 发现缺陷: Exit 1 ]     [ 安检干净: Exit 0 ]
                    │                       │
                    ▼                       ▼
           PR 立即打回，阻断流水线    ┌─────────────────────────────────┐
           不浪费昂贵的云端算力     │ Stage 2: 全量单测/集成测试/构建 │
                                    └───────────────┬─────────────────┘
                                                    │
                                                    ▼
                                    ┌─────────────────────────────────┐
                                    │ Stage 3: pi-review panel (深度) │
                                    └─────────────────────────────────┘
```

### 场景三：大仓变更文件（Monorepo Diff）前置分诊
在大型 Monorepo 场景下，某次提交流水线可能涉及几十个模块修改。
通过 `pi-review screen` 对变更文件进行极速探测，仅将打出「高风险」或「未匹配信号」的核心文件分流至后续深度多评委审查，避免全量文件无差别调用大模型。

### 场景四：配合 Loop 的自动化收敛闭环
当 Agent 自主进行代码修复（如 `pi-review loop --until clean`）时，在每一轮调用昂贵的大模型面板之前，先通过 `screen` 做快速冒烟检查：
- 若最基本的语法与模式级缺陷还没修好，直接驳回并提供针对性反馈，不浪费完整评委的上下文与 Token。

### 总结
- **`screen` 不是来取代深度审查的，而是来重塑准入分工的**。
- 它承担了传统大模型「想做却因为太慢而做不好」的高频前置卡口职责；
- 将 **1 秒级的模式拦截** 与 **分钟级的语义会诊** 组合，构成了现代 AI 代码审查最优雅的工程闭环。
